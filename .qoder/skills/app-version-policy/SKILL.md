# 通用应用版本与更新记录规则

本 Skill 是给 agent 用的判定规则：判断"这一轮是否需要递增应用版本号并维护项目更新记录"。

核心判断：这次改动是否会影响应用的运行、发布、功能、接口、配置、用户可见产品体验或后续版本维护？只有答案明确为"是"时，才使用本 Skill。

## 适用范围

### 触发本 Skill

本轮修改了可运行应用/产品交付物，且属于开发迭代时，触发本规则：

- 代码修改；
- 应用运行配置修改；
- 构建、打包、部署或发布配置修改；
- 数据库 schema、迁移脚本、接口契约或 API 配置修改；
- 用户可见产品文案、页面内容或应用内帮助文档修改；
- 会影响功能、交互、权限、数据流、性能、安全或兼容性的项目结构修改；
- 与本次应用开发改动直接配套的 README、部署说明、用户手册等交付文档修改。

### 不触发本 Skill

以下情况即使修改了文件，也不要递增版本号，也不要新增项目更新记录：

- 仅回答问题或解释概念；
- 仅整理知识、笔记、问答、会议纪要、调研材料、学习材料；
- 仅创建或更新知识库文档，例如 `AI知识库.md`、`知识库.md`、`学习笔记.md`；
- 仅整理方案文档、需求草稿、测试记录、资源清单、Excel/Word/PPT 等非应用交付物；
- 只读取文件、搜索文件、查看日志，未修改应用交付物；
- 只排查原因但没有实施应用修复；
- 只修改 agent 自身配置、Skill、个人工作流或记忆文件；
- 只对本 Skill 或其它 Skill 做维护；
- 用户明确要求"不要更新版本/不要写更新记录"；
- 当前目录不是一个可运行应用项目，且本轮只是资料处理或文档整理。

### 边界规则

- "项目文档"先判断是否属于应用交付的一部分：部署说明、用户手册、应用内帮助文档可以触发；知识整理、会议纪要、调研材料不触发。
- "测试方案/资源需求/部署方案"等项目管理材料默认不触发，除非用户明确要求把它作为应用版本交付的一部分。
- 仅生成一次性报告或整理表格，默认不触发。
- 不确定是否触发时：先不要更新版本和更新记录，在最终回复中说明"本次未按应用开发更新记录处理，因为改动不属于应用交付物"。

## 触发检查清单

在使用本 Skill 前，先逐项判断：

1. 本轮是否修改了文件？
2. 修改的文件是否属于可运行应用/产品交付物？
3. 修改是否会影响功能、配置、发布、接口、用户体验或维护版本？
4. 用户是否没有明确排除更新记录？

四项全部为“是”时，才递增版本并维护更新记录。

任一项为“否”时，不使用本 Skill。

## 版本号规则

- 每完成一轮应用开发修改后，默认递增一个 patch 版本号，除非用户指定其它版本规则。
- 先查找项目既有版本来源：`package.json` 的 `version`、`app.json` / `app.config.*`、移动端原生版本配置、项目已有的 `version.ts` / `constants.ts` / `config` 文件、页面中已经展示的版本号。
- 已有集中版本来源就沿用；没有时不要为了普通文档任务创建版本配置；只有确认为应用项目、且本轮确实是应用开发变更时，才考虑创建清晰的版本配置文件。
- 应用类项目应在用户可见位置展示版本号，例如"我的""设置""关于"等页面。
- 不要在多个文件中手写互相独立的版本号；如必须同步多个平台版本，应在修改后确认它们一致。

## 更新记录规则

- 每完成一轮应用开发修改后，把本轮更新内容写入项目内的更新记录 md。
- 如果项目已有更新记录文件，沿用已有文件。
- 如果项目没有更新记录文件，且本轮确认为应用开发变更，才在项目根目录创建：

```text
更新记录.md
```

- 更新记录的目标读者是**最终用户和应用使用者**，不是开发流水。读者应当能感知到"这次改动在产品层面意味着什么"，而不是"代码里动了什么"。
- 每条更新用面向用户的方式描述。例如：
  - 推荐写法：「首页背景动效在滚动到列表时自动暂停，回到首页时再恢复，浏览时更省电」
  - 不推荐写法：「在 Hero 组件的 useEffect 中注册 IntersectionObserver，滚动离开时取消 rAF」
- 不写内部实现细节(文件路径、组件名、参数名、token 名、依赖包名、代码改动行号),不写普通问答、知识整理、资料汇总、调研摘要、临时文件处理、命令输出和排查流水。
- 推荐结构：

```md
# 更新记录

## v0.1.2 - 2026-05-17

- 首页背景动效在滚动到列表时自动暂停，回到首页时再恢复。
- 浏览器标签加上桑葚小图标，标题简化为「桑葚集」。
- 修复浅色模式下首页标题显示为深色的问题。
```

- 每次新增记录放在文件顶部较新的位置，便于查看最近更新。
- 如果本轮不触发本 Skill，不要为了说明“不触发”而写入更新记录。

## Git 提交描述规则

当用户明确要求提交 git，且本轮触发了应用版本更新时，提交描述必须包含当前版本号。

推荐格式：

```text
v0.1.2 简短说明
```

不要因为版本号变化就自动提交。

## 验证

修改版本号和更新记录后，应在可行时运行项目常规检查命令：

- TypeScript 项目：`npx tsc --noEmit`
- Web 项目：`npm run build`
- 其它项目：优先使用项目 README、脚本或既有工作流中的验证命令。

如果无法运行验证，需要在最终回复中说明原因。

## 其它

- 本 Skill 的重点是"应用开发迭代记录"，不是"所有文件改动审计"。宁可少触发，也不要把学习资料、问答整理和个人工作流维护写入应用更新记录。
- 如果用户专门要求"把这份文档也记入更新记录"，可按用户要求处理，但最终回复中说明这是用户指定的文档记录，不是默认应用开发触发。
